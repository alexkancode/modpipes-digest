What v0 got right, and why

The builder's v0 design produced a clean first run. These choices carry over to the next desktop or file-deleting pipeline.

Worked in a runPreflight that asks once per blocker, then stops

The stress run made 4 checks and 3 AskUserQuestion calls, one per round and none in parallel. It never ran --relaunch-firefox, kept ok: false and skipped every later stage. The report then named both ClamAV fixes.

Why the design worked: the preflight script owns the facts in status.json, and the model only relays blockers. The model cannot talk itself past a missing scanner.

Worked in a runDeletion only through one guarded call

deletions.csv holds 4 rows, all .incoming/*.part paths inside the Pinterest folder. No .part files were left behind.

Why the design worked: the toolkit is a script stage, so guard.safe_remove is the same code every run. A unit test greps every other module for os.remove, rmtree, glob and shell=True.

Worked in a runLinks stay out by construction

A regex for http|pinimg|pinterest.com over all 5 catalogue rows found 0 hits. A grep over the outputs and the Pinterest folder found no links.

Why the design worked: only the fetch script reads the manifest, and the report scrubs every line. The same scrub caused defect 1, described below.

Worked in a runThe accessibility tree was enough

The driver read board and pin links on the first try (via: tree). The view-source fallback for board pages was not needed. Firefox view-source resolved 5 of 6 pins.

Each change, with its evidence

Confirmed offlinev1: the Limits line no longer scrubs itself

Defect
v0 printed "No Pinterest or [removed] link". scrub() removes any word that holds pinimg, and the fixed text named that domain word.
Change
The line now says "its image host". A unit test asserts the clean line.
Evidence
The tester replayed v1 and v3 report.py on both runs' inputs. replay-v3-report.md holds 0 [removed].
Why it works
When a scrubber runs over every line, fixed text has to avoid the scrub words. The change moves the text, and the scrub stays strict.

No effect in a runv2: the driver lock never refuses

Defect
Two runs could type into one Firefox at the same time.
Change
claim() writes ~/.modpipes/pinterest-driver.owner under flock before each keystroke. The claim reads the run id from MODPIPES_RUN_ID.
Evidence
  • server/src/engine/scriptEnv.ts sets MODPIPES_RUN_ID for script stages only.
  • In v3 the driver's run.kind is model. This analysis stage is also a model stage, and env | grep MODPIPES here shows no run id.
  • A replay with the variable unset let run A and then run B claim. Both wrote {"run": "manual"}. File: k8n7vfc/work/replay/claim-replay.txt.
  • The tester's unit test patched MODPIPES_RUN_ID in, so the test passed.
Second gap
No call releases the claim. Once the run id works, a rerun within 10 minutes of a finished run would be refused.
Next
Pass the run id to drive.py as an argument, read from the manifest output path. Add drive.py release as the driver's last step.

Confirmed offlinev3: board and pin labels lose their profile chrome

Defect
Board names read like "Edit Clay , 38 Pins , 3h", and pin titles ended in "pin page". The driver model cleaned the names by hand.
Change
board_name() and pins_in() strip the chrome, with 2 unit tests.
Evidence
  • All 120 board labels in the driver transcript carried chrome before v3. None carried chrome after v3.
  • "Private board icon Edit Gardigan , 80 Pins , 3d" becomes "Gardigan".
  • All 31 pin titles ended in "pin page" before v3. None ended in "pin page" after v3.
  • File: k8n7vfc/work/replay/labels-replay.txt.
Why it works
The helper now returns names the model can copy, so the manifest no longer depends on model judgment.

Partialv3: a skipped pin is replaced from the same board

Confirmed offlinev3: the summary counts only rejected deletions
