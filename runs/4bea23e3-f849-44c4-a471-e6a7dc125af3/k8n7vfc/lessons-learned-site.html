What improved, and why

1. The two-gate loop stop confirmed, 2 of 2

The polish loop stops only when report.json says ok and verdict.json says ship. In round 1 the critic shipped both pages, at 84 and 82, with zero blockers. The checker failed 11 and 14 checks on those same pages. The stop condition forced round 2, and round 2 fixed every failure from the report.

Why it works: the critic reads screenshots and cannot click through a frame. The checker clicks, reloads and frames the page. Each gate catches failures the other cannot see.

2. Round 2 reading the report confirmed, 2 of 2

The page prompt says to fix every failed check first when a report is present. Diffing each run's round-1 page against its final page shows a fix for every failure:

  • Stress: the Next links gained data-next, and each screen gained data-screen.
  • Happy: the h2 text was renamed to "Setup at ads.openai.com" and "Tracking". No data-screen was added. The page now opens step 1 on a reload. It now writes Copied on the button and skips the clipboard call in the frame. Images load eagerly.

The two pages fixed the same check in two ways, matching whichever guess that run's checker made. That points to the root cause below.

3. v1 contract hooks: data-screen, data-next, data-back predicted, likely

No run has used v1. Both generated checkers already query [data-next] first and include dataset.screen in their screen label. A v1 page that follows the contract should therefore satisfy any checker built the way these two were. The v1 toolkit prompt still describes checks as "clicking Next" and "the creatives, setup and tracking screens". It never names the selectors, so a future checker could still guess differently.

  • check.cjs:80 in happy and check.cjs:59 in stress, under stages/toolkit/outputs/tools/, hold the locators. check.cjs:178 and :177 build the screen labels.

4. v1 framed clipboard rule predicted, likely

Both round-1 pages called navigator.clipboard inside the sandboxed frame. The browser logged a Permissions-policy console error, and the no-errors check failed in framed mode in both runs. The happy round-2 page skipped the call when sandboxed and passed. v1 states the same rule in the shared prompt.

5. v1 copywriter targetUrl without a query string predicted

The happy copywriter wrote https://instideck.com/?utm_source=chatgpt&…&utm_term={ad_id}. The ad plan wrote /chatgpt?utm_term=A. The page used the plan's URLs, so the user never saw the conflict. The stress copywriter wrote null, which was correct because there is no live URL. v1 gives tracking to ad-plan alone. That removes one of the two sources of truth.

6. v2 eager images predicted, likely

The happy round-1 page had five loading="lazy" images. In framed mode all five read naturalWidth 0 on hidden screens. The final page dropped the attribute and passed. v2 forbids lazy loading in the page prompt.

Root cause behind all six: the toolkit stage writes check.cjs fresh in each run, and a different model stage writes the page. Any hook the shared contract leaves unnamed gets guessed twice, once by each stage. The two runs' checkers even named their checks differently: 24 checks in one, 23 in the other. The durable fix is a contract that names every selector and state the checker tests, repeated line by line in the toolkit prompt.
