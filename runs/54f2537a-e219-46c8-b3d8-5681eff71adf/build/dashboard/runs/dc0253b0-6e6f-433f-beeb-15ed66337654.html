  3. Confirm with the user asked · answered · Fri 6 Nov, 10:45

    Here is my understanding of the new pipeline, Game forge iterate. Does this match what you want? Start: a variable names a finished Game forge run (or an earlier iterate run, since its final outputs keep the same shape). Blank means the latest finished Game forge run. Understand: one stage copies the delivered game into this run, reads report, GDD, art direction, asset plan, tech plan, play-test scores and screenshots, and writes a digest of what the game is, how it is built, and what the report said a next iteration should tackle. First ask: you see the playable game beside the question (inline, plus a clickable link that opens it as a page) and say what to change, with options drawn from the digest plus Other. Follow-up questions pin specifics, one question per call. Loop, up to a cap of 20 rounds, each round roughly 10 to 20 minutes: - research reads your feedback and looks up how games solve that kind of thing, then writes a change plan; no options come back to you - code and art change in parallel, keeping Game forge's contracts (asset-plan.json, window.__game, ?seed) so the harness still works - smoke every round, bots when the source run has a harness; the implementer fixes what the bots break - a script verifies the build loads, starts and runs clean - ask: you see the new build inline and by link with a short note of what changed, and say what next, or done. A build that failed verification is shown honestly with fix it as the first option. The loop ends when you say done. Deliver then packages the final game, a report with the per-round changelog, and a play link, all starred. Every round's build stays on disk under rounds/<n>. Models: opus for research, code and art; sonnet or haiku for digest, ask and deliver; scripts for verify and bots.
